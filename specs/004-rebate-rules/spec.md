# Feature Specification: 系统设置 - 返佣规则模块

**Feature Branch**: `004-rebate-rules`  
**Created**: 2026-04-19  
**Status**: Draft  
**Input**: User description: "设计系统设置-返佣规则模块需求，用户端通过 agent 市场订阅 agent，可以给 agent的创作者进行返拥，按照订阅数量*返佣单价=返佣金额，这里返佣规则模块主要是负责定价，和防套利规则设定，帮我基于上述描述继续完善需求"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员配置返佣定价规则 (Priority: P1)

超级管理员或具备权限的管理员进入系统设置的返佣规则页面，可以新增、编辑、启用/停用返佣定价规则。每条规则定义返佣单价（如每订阅 1 个 agent 返佣 X 元），并可选择适用对象（全局默认或指定 Agent）。规则生效后，用户订阅行为产生的返佣金额按此规则自动计算。

**Why this priority**: 返佣定价是整个返佣体系的核心基础，没有定价规则就无法产生返佣金额，其他防套利、统计功能均依赖于此。

**Independent Test**: 管理员在后台新增一条返佣规则（单价 5 元），前端用户完成一次 agent 订阅，验证返佣记录中金额 = 1 * 5 = 5 元。

**Acceptance Scenarios**:

1. **Given** 管理员已登录后台，**When** 进入返佣规则设置页并新增一条规则（单价 10 元，状态启用），**Then** 规则保存成功并出现在规则列表中
2. **Given** 已存在一条启用的返佣规则，**When** 管理员编辑该规则将单价从 5 元改为 8 元，**Then** 新产生的订阅按 8 元计算，历史已产生的返佣金额保持不变
3. **Given** 已存在一条启用的返佣规则，**When** 管理员停用该规则，**Then** 新订阅不再产生返佣，但已产生的返佣记录不受影响
4. **Given** 系统中已有一条全局返佣规则，**When** 管理员再新增一条全局返佣规则，**Then** 系统提示"已存在全局规则，请先停用现有规则"

### User Story 2 - 管理员配置防套利规则 (Priority: P2)

管理员可以在返佣规则模块中设定防套利策略，以防范创作者通过自订阅、多账号刷单等方式骗取返佣。防套利规则包括但不限于：同一设备/IP 短期内多次订阅的拦截、创作者不得订阅自己创建的 Agent、新注册用户短时间内大量订阅的阈值限制等。

**Why this priority**: 防套利是保障平台资金安全的关键风控措施。如果返佣定价规则上线但缺少风控，平台将面临巨大的资金损失风险。

**Independent Test**: 模拟同一 IP 地址在短时间内连续订阅 10 次，验证系统根据防套利规则进行拦截或标记，不产生全部返佣金额。

**Acceptance Scenarios**:

1. **Given** 防套利规则已启用"同一用户不可订阅自己创建的 Agent"，**When** 创作者尝试使用自己的账号订阅自己创建的 Agent，**Then** 订阅成功但返佣金额记为 0，并记录套利预警日志
2. **Given** 防套利规则已启用"同一 IP 24 小时内最多产生 3 次有效返佣"，**When** 同一 IP 在 1 小时内完成 5 次订阅，**Then** 前 3 次产生正常返佣，后 2 次返佣金额记为 0 并标记为疑似套利
3. **Given** 防套利规则已启用"新注册用户 7 天内订阅超过 10 个 Agent 触发风控"，**When** 一个注册 3 天的用户订阅了第 11 个 Agent，**Then** 该笔订阅的返佣进入"待审核"状态，不立即结算
4. **Given** 管理员在后台调整防套利阈值（如将同一 IP 限制从 3 次改为 5 次），**When** 保存配置后，**Then** 新发生的订阅行为按新阈值执行，历史已标记的行为不受影响

### User Story 3 - 管理员查看返佣统计数据 (Priority: P3)

管理员可以在后台查看返佣相关的统计数据，包括：各 Agent 的订阅量及对应返佣金额汇总、疑似套利事件列表、返佣结算趋势图表、按创作者维度统计的返佣排名等。支持按时间范围、Agent、创作者等维度筛选和导出。

**Why this priority**: 统计数据是运营决策和财务对账的依据，属于增值功能。定价规则和防套利规则上线后即可运行，统计页面可以后续迭代补充。

**Independent Test**: 产生若干订阅和返佣记录后，管理员进入返佣统计页，验证各维度的汇总数据与明细记录一致。

**Acceptance Scenarios**:

1. **Given** 系统中已产生返佣记录，**When** 管理员进入返佣统计页并选择本月时间范围，**Then** 页面展示本月总返佣金额、总订阅数、疑似套利笔数等关键指标
2. **Given** 管理员在返佣统计页，**When** 按创作者维度筛选某个特定创作者，**Then** 展示该创作者下各 Agent 的订阅量和返佣金额明细
3. **Given** 管理员在疑似套利事件列表页，**When** 对某条标记为"疑似套利"的记录点击"确认正常"，**Then** 该记录返佣状态变更为"正常结算"，对应金额进入可结算状态
4. **Given** 管理员在返佣统计页，**When** 点击"导出 CSV"按钮，**Then** 系统生成包含当前筛选条件下的返佣明细 CSV 文件并触发下载

### Edge Cases

- 当返佣规则停用期间发生订阅，系统如何处理？（不产生返佣）
- 当同时存在全局规则和一个 Agent 的专属规则时，优先使用哪个？（专属规则优先于全局规则）
- 激励规则按单笔订阅的实时数量计算，订阅发生时立即按超额累进方式分段计算返佣
- 若单笔订阅数量跨越多个激励区间，各区间数量分别按对应系数计算后加总
- 返佣单价如果设置负数或零，系统是否允许？（不允许负数，零值允许但不产生返佣）
- 创作者账号被禁用后，其名下 Agent 的历史返佣记录和待结算返佣如何处理？（历史已结算不受影响，待结算暂停直至账号恢复）
- 订阅发生退款/退订时，已产生的返佣如何处理？（对应返佣记录标记为"已退回"并从可结算金额中扣除）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持管理员在后台创建返佣定价规则，每条规则至少包含：规则名称、返佣单价（元/订阅）、适用对象（全局默认或指定 Agent）、生效时间范围、状态（启用/停用）。每条定价规则可关联一组阶梯激励规则
- **FR-002**: 系统在同一时间范围内，同一 Agent 只能有一条生效的定价规则；全局规则同一时间只能有一条生效
- **FR-003**: 当订阅发生时，系统必须根据当前生效的返佣定价规则自动计算返佣金额。基础计算公式为：返佣金额 = 订阅数量 × 返佣单价 × 系数（默认系数为 1）。若定价规则关联了激励规则，则按超额累进方式计算：将该笔订阅数量按激励区间分段，各区间的数量分别乘以该区间的激励系数后加总。例如订阅 30 个，规则为 1-10 系数 1.0、11-50 系数 1.2，则返佣 = 10×单价×1.0 + 20×单价×1.2
- **FR-004**: 系统必须支持管理员配置防套利规则，至少包含以下策略维度：创作者自订阅拦截、同一 IP/设备频次限制、新注册用户行为阈值、关联账号检测
- **FR-005**: 防套利规则触发时，对应的返佣记录不应进入"已结算"状态，而是进入"已拦截"或"待审核"状态，并记录触发原因
- **FR-006**: 管理员可以对被标记为"待审核"的返佣记录进行人工审核操作（确认正常 / 确认套利），审核结果影响该记录的结算状态
- **FR-007**: 系统必须提供返佣统计数据看板，包含：总返佣金额、总订阅数、待审核笔数、已拦截笔数、按时间趋势汇总
- **FR-008**: 统计数据必须支持按时间范围（日/周/月/自定义）、Agent、创作者等维度筛选
- **FR-009**: 管理员可以将返佣明细和统计数据导出为 CSV 格式
- **FR-010**: 返佣规则的配置变更（定价调整、停用/启用）只影响变更后的新订阅行为，不影响已产生的返佣记录

### Key Entities *(include if feature involves data)*

- **RebateRule（返佣定价规则）**: 定义返佣单价及适用范围，包含规则名称、单价金额、适用 Agent（可为空表示全局）、生效起始时间、生效结束时间、状态、创建人、创建时间。可关联一组 IncentiveRule
- **IncentiveRule（阶梯激励规则）**: 定义单笔订阅数量区间对应的激励系数，包含关联的 RebateRule ID、区间下限、区间上限、激励系数（默认 1.0 表示无额外激励）。同一 RebateRule 下的多条 IncentiveRule 按区间连续排列，无重叠无间隙，订阅发生时按超额累进方式分段计算
- **RebateRecord（返佣记录）**: 记录每一次订阅行为对应的返佣明细，包含关联的订阅订单、Agent、创作者、返佣金额、计算依据的规则 ID、状态（待结算/已结算/已拦截/待审核/已退回）、防套利触发标记。订阅发生时实时计算并写入记录，T+1 后自动变更为"已结算"
- **AntiArbitrageRule（防套利规则）**: 定义各类风控策略及阈值，包含策略类型（自订阅拦截/IP 频次/新用户阈值/关联账号）、规则参数（如 IP 频次阈值、时间窗口）、处理动作（直接拦截/标记待审）、状态
- **RebateAuditLog（返佣审核日志）**: 记录管理员对疑似套利返佣记录的人工审核操作，包含审核人、审核时间、审核结论、备注

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可以在 3 分钟内完成一条返佣定价规则的配置（从进入页面到保存成功）
- **SC-002**: 系统能在订阅行为发生后 1 秒内完成返佣金额的计算并写入返佣记录
- **SC-003**: 返佣统计数据页面的加载时间不超过 500 毫秒（数据量 10 万条以内）
- **SC-004**: 防套利规则对已知套利场景的识别准确率不低于 95%（同一 IP 高频刷单、创作者自订阅等典型场景）
- **SC-005**: 返佣模块上线后，因套利行为导致的平台资金损失降低至少 80%（相比无风控规则的基准期）
- **SC-006**: 返佣明细导出功能支持单次导出最多 10 万条记录，导出耗时不超过 10 秒

## Clarifications

### Session 2026-04-19

- Q: 激励规则中的"订阅数量"是指单笔订阅的实时数量，还是创作者在某一结算周期内的累计订阅量？ → A: 单笔订阅实时计算。每次订阅发生时，根据该笔订阅数量按激励区间超额累进分段计算返佣（默认系数 1，仅超出部分按对应区间系数计算）
- Q: 防套利规则是在订阅发生时实时拦截，还是事后通过定时任务批量扫描修正？ → A: 订阅时实时拦截。返佣记录写入前同步完成防套利校验，触发规则的直接标记为"已拦截"或"待审核"
- Q: 返佣金额是实时到账还是周期结算？ → A: 订阅发生时实时计算返佣金额并写入记录，但实际到账（可提现）采用 T+1 模式，即次日到账。返佣记录状态为"待结算"，T+1 后自动变更为"已结算"

## Assumptions

- 订阅行为由现有 agent 订阅模块触发，返佣规则模块通过事件/消息机制接收订阅事件，不直接处理支付流程
- 创作者与 Agent 的归属关系已在现有系统中建立，返佣规则模块可直接读取
- 返佣结算的实际打款流程（如对创作者进行转账）不在本模块范围内，本模块只负责金额计算和记录，结算打款由财务系统对接
- 用户端的 agent 市场订阅流程本身不在本需求范围内，本模块仅关注返佣规则的制定和返佣金额的计算
- 退款/退订流程由订单系统处理，本模块通过监听退款事件来回退对应返佣记录
- 防套利规则在订阅发生时实时执行，返佣记录写入前同步完成风控校验
- 返佣金额采用 T+1 结算模式：订阅发生时实时计算并写入返佣记录（状态"待结算"），次日自动变更为"已结算"，创作者方可提现
