# Research: 短信验证码登录

**Feature**: 用户短信验证码登录
**Date**: 2026-04-22

## 决策记录

### 1. SMS 服务商选择

**Decision**: 使用抽象接口 + 阿里云短信作为首选实现，开发环境提供 Mock 实现

**Rationale**:
- 项目已部署在中国大陆环境，阿里云短信国内到达率和稳定性最佳
- 通过接口抽象，可零成本切换为腾讯云、华为云等其他服务商
- 开发/测试环境使用 Mock 实现，避免真实发送短信产生费用和依赖外部服务
- 不引入第三方 SMS SDK（如 Twilio），减少依赖；直接调用阿里云 OpenAPI HTTP 接口即可

**Alternatives considered**:
- 腾讯云短信：同样稳定，但项目已有阿里云 OSS 集成，保持云服务商一致更便于运维
- 第三方聚合 SDK（如极光、容联七陌）：增加额外依赖，接口封装未必优于直接调用
- 仅 Mock：无法在生产环境使用，不可接受

### 2. 验证码存储方案

**Decision**: Redis 字符串 + TTL，Key 格式 `sms:login:{phone}`

**Rationale**:
- 项目已有 Redis 基础设施（go-redis/v9），零额外部署成本
- Redis TTL 天然支持过期自动清理，无需定时任务
- 验证码生命周期短（5 分钟）、读写频繁，Redis 性能远优于数据库
- 防重发 also stored in Redis: `sms:limit:{phone}` with 60s TTL

**Alternatives considered**:
- PostgreSQL + 定时任务清理：引入不必要的数据持久化和维护负担
- 内存缓存：多实例部署时无法共享状态

### 3. 手机号校验规则

**Decision**: 中国大陆手机号正则 `^1[3-9]\d{9}$`，输入时自动过滤空格和横线

**Rationale**:
- 中国大陆手机号固定 11 位，以 1 开头，第 2 位为 3-9
- 正则校验前后端均需实现，前端即时反馈，后端兜底
- 不过度复杂化（如按号段细分），避免运营商新号段导致校验失败

### 4. 登录凭证方案

**Decision**: 完全复用现有 JWT 体系（access_token + refresh_token + httpOnly Cookie）

**Rationale**:
- 后端已有成熟的 JWT 生成、解析、刷新、黑名单机制
- 短信登录成功后的凭证发放与现有邮箱/密码登录完全一致
- 前端 auth store 无需改动，登录成功后调用相同的 `login(token, user)` 即可
- 保持所有登录方式的凭证格式统一，便于后续维护和权限校验

### 5. 前端登录页交互设计

**Decision**: 在现有登录页面增加 "账号密码登录 / 手机号登录" Tab 切换

**Rationale**:
- 不新增独立路由，减少页面跳转和路由维护成本
- 用户可在同一页面快速切换登录方式
- 复用现有的页面样式（auth-container、auth-card、auth-header 等 CSS）
- 微信一键登录按钮在短信登录 Tab 下仍可展示，保持多端一致性

### 6. 自动注册策略

**Decision**: 短信验证成功后，若手机号未注册则自动创建用户账户

**Rationale**:
- 符合用户描述中 "自动注册 / 登录" 的诉求
- 简化用户流程，无需先注册再登录
- 新用户自动注册时：`phone` = 手机号，`register_source` = `"sms"`，`nickname` 可默认为隐藏部分手机号的名称（如 "138****8000"），`username` 可设为随机或同样用手机号
- 用户后续可在个人中心补全邮箱、设置密码

### 7. 安全与防刷策略

**Decision**: 三层防护
1. **单手机号频率限制**：60 秒内不可重复发送（Redis `sms:limit:{phone}`）
2. **单 IP 频率限制**：同一 IP 每分钟最多发送 10 条验证码（Redis `sms:limit:ip:{ip}`）
3. **图形验证码**：连续发送失败 3 次后，要求输入图形验证码（Phase 2 可扩展）

**Rationale**:
- 60 秒防重发是行业标配，平衡用户体验和防刷
- IP 限制防止攻击者轮换手机号刷接口
- 图形验证码作为进阶防护，本功能 Phase 1 先实现前两层，图形验证码作为可选增强
