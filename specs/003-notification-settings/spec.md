# Feature Specification: 通知设置管理

**Feature Branch**: `003-notification-settings`
**Created**: 2026-04-19
**Status**: Draft
**Input**: User description: "系统设置->通知设置，交互形式是列表页面，可以在列表页面新建通知，在通知创建页面进行编辑，编辑内容：1.标题，2. 生效时间，3.可见群体（用户等级）4.消息内容；先实现后台部分，前台部分后续单独做需求澄清和实现"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员创建并发布系统通知 (Priority: P1)

系统管理员需要向不同等级的用户发布系统通知。管理员进入系统设置中的通知设置页面，查看现有通知列表，点击新建通知，填写标题、生效时间、可见群体和消息内容，保存后通知按生效时间自动展示给对应用户。

**Why this priority**: 这是通知管理系统的核心功能，没有它整个特性无法交付价值。

**Independent Test**: 可以独立测试通知的增删改查，并通过接口验证数据是否正确存储和按条件过滤返回。

**Acceptance Scenarios**:

1. **Given** 管理员已登录并进入通知设置页面，**When** 点击新建通知并填写完整信息（标题、生效时间、可见群体、消息内容）后保存，**Then** 通知成功保存，列表页出现该通知
2. **Given** 管理员在编辑通知页面，**When** 修改通知内容并保存，**Then** 更新后的内容即时生效
3. **Given** 管理员在通知列表页，**When** 对一条通知执行失效操作，**Then** 该通知状态变为"已失效"，对应用户不再看到此通知

---

### User Story 2 - 用户按等级查看生效通知 (Priority: P2)

普通用户登录后，系统根据其用户等级和当前时间，自动展示对其可见且已生效的通知内容。

**Why this priority**: 这是通知发布的最终目的——触达用户。虽然依赖后台管理功能，但可以独立验证通知的可见性过滤和生效时间控制是否工作正常。

**Independent Test**: 可以通过接口模拟不同等级用户访问，验证返回的通知列表是否按用户等级和生效时间正确过滤。

**Acceptance Scenarios**:

1. **Given** 用户等级为 VIP，当前时间在通知生效时间范围内，**When** 用户查看通知列表，**Then** 看到所有对 VIP 及以上等级可见的通知，紧急消息在前、普通消息在后，同类型无序展示
2. **Given** 用户等级为普通用户，**When** 用户查看通知列表，**Then** 仅看到对普通用户及以上等级可见的通知，看不到仅限高等级用户的通知
3. **Given** 当前时间未到达某通知的生效时间，或已超过失效时间，**When** 任何用户查看通知，**Then** 该通知不出现


---

### User Story 3 - 通知列表管理与筛选 (Priority: P3)

管理员需要高效管理大量通知，能够查看通知列表、按状态筛选（生效中/未生效/已过期）、快速定位特定通知。

**Why this priority**: 提升管理效率的辅助功能，可以在核心功能完成后独立实现。

**Independent Test**: 可以独立测试列表查询、分页、筛选功能是否按预期返回正确数据。

**Acceptance Scenarios**:

1. **Given** 通知列表有 20 条通知，**When** 管理员翻页查看，**Then** 分页功能正常工作，每页显示固定数量
2. **Given** 管理员选择筛选"生效中"，**When** 列表刷新，**Then** 仅显示当前处于生效时间段内的通知

---

### Edge Cases

- 生效时间结束时间早于开始时间时，系统拒绝保存并返回校验错误（已在 FR-014 中明确）
- 紧急消息和普通消息在管理端列表中是否需要标识区分？
- 通知内容超长（如超过数据库字段限制）时如何处理？
- 管理员将可见群体设为空（所有等级）时，是否所有用户都可见？
- 通知生效时间跨天时区问题如何处理？
- 正在编辑的通知被另一个管理员同时修改，如何处理冲突？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供通知列表查询接口，支持分页返回通知数据
- **FR-002**: 系统 MUST 支持管理员创建新通知，包含标题、消息类型、生效时间、可见群体、消息内容五个字段；消息类型分为普通消息和紧急消息两种
- **FR-003**: 系统 MUST 支持管理员编辑未失效通知（待生效、生效中）的全部字段；已失效通知不支持编辑
- **FR-004**: 系统 MUST 支持管理员将通知标记为"已失效"；通知不允许物理删除，只能通过失效操作使其对用户不可见
- **FR-005**: 系统 MUST 根据当前时间和请求用户等级，过滤返回对其可见且已生效的通知
- **FR-006**: 生效时间 MUST 支持配置开始时间和结束时间，开始时间必填，结束时间可选（为空表示永久生效）
- **FR-007**: 可见群体 MUST 基于用户等级体系进行配置，通过设置"最低可见等级"实现；等级数值 ≥ 该值的用户均可见此通知
- **FR-008**: 系统 MUST 提供通知详情查询接口，返回完整的通知内容
- **FR-009**: 通知列表 MUST 在每条通知上展示其当前状态（待生效 / 生效中 / 已过期 / 已失效）
- **FR-010**: 通知列表 MUST 支持按状态筛选（全部 / 待生效 / 生效中 / 已过期 / 已失效）
- **FR-011**: 通知列表 MUST 支持按创建时间倒序排列，最新的通知排在最前
- **FR-012**: 通知列表的操作列 MUST 支持"失效"操作；处于"待生效"或"生效中"状态的通知均可被失效
- **FR-013**: 通知列表的操作列 MUST 支持"复制"操作；点击复制后基于原通知内容快速创建一条新通知副本，管理员可在此基础上修改后保存发布
- **FR-014**: 创建和编辑通知时，系统 MUST 校验生效结束时间必须严格晚于开始时间；若校验失败则拒绝保存并返回明确的错误提示

### Key Entities *(include if feature involves data)*

- **通知 (Notification)**: 代表一条系统通知。核心属性包括：标题（简短文本）、消息类型（普通 / 紧急）、生效时间范围（开始时间、可选的结束时间）、可见群体（最低可见用户等级）、消息内容（支持富文本的长文本）、状态（待生效 / 生效中 / 已过期 / 已失效）、创建/更新时间。
- **用户等级 (UserLevel)**: 表示用户在系统中的等级分类。通知通过关联一个或多个用户等级来决定可见范围。假设等级体系已在用户模块中定义。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可以在 30 秒内完成一条新通知的创建并保存
- **SC-002**: 通知列表查询响应时间在 100 条数据以内不超过 500 毫秒
- **SC-003**: 不同等级用户只能看到对其可见的通知，可见性过滤准确率 100%
- **SC-004**: 通知在到达生效开始时间后，用户端在 1 分钟内可以看到；超过结束时间后，用户端在 1 分钟内不再显示
- **SC-005**: 支持同时管理至少 1000 条历史通知记录而不影响查询性能

## Clarifications

### Session 2026-04-19

- Q: 通知列表的操作和删除策略是什么？ → A: 通知不允许物理删除，列表操作列支持"失效"功能；无论是待生效还是生效中的通知都可以被失效。列表上需要展示通知状态。
- Q: 用户等级与可见群体过滤逻辑是什么？ → A: 用户等级使用数值表示（如 1=普通, 2=VIP, 3=SVIP），通知配置"最低可见等级"，等级数值 ≥ 该值的用户均可见（即高等级用户可以看到低等级可见的通知）。
- Q: 已失效通知是否可以恢复？未生效/生效中的通知是否支持编辑？ → A: 已失效的通知不支持恢复，为终态。列表支持"复制"功能，可基于原通知快速创建副本重新编辑发布。未失效的通知（待生效、生效中）均支持编辑。
- Q: 用户端查看多条通知时的排序规则是什么？ → A: 通知有优先级属性，根据消息类型区分：1=普通消息（如版本更新），2=紧急消息（如重大故障）。用户端按优先级分组展示，紧急消息在前，普通消息在后；同优先级消息之间无序展示。管理端通知列表按创建时间倒序排列。
- Q: 生效时间结束时间早于开始时间时，系统如何处理？ → A: 前后端均进行校验，结束时间必须严格晚于开始时间；若违反则拒绝保存并返回明确的校验错误提示。

## Assumptions

- 用户等级体系已在现有用户模块中定义，通知功能直接引用已有等级枚举/配置
- 前台展示逻辑（用户端如何渲染通知）不在本次后台实现范围内，后续单独澄清
- 通知内容编辑支持富文本（HTML），但具体富文本编辑器选型由前端需求确定
- 系统使用单一时区（Asia/Shanghai）处理生效时间，暂不考虑多时区用户场景
- 管理员权限校验由现有认证/鉴权中间件处理，通知模块本身不重复实现
