# 股票分析智能应用 - 技术架构设计

## 1. 系统概述

### 1.1 目标
- **核心目标**: 在个股涨停前及时捕捉机会
- **关键指标**: 实时性、成功率
- **学习能力**: 通过每日复盘优化决策Agent

### 1.2 架构选型
- **架构模式**: C/S架构
- **后端**: Python技术栈（异步高性能）
- **前端**: React (H5) - 跨平台展示

## 3. 核心模块设计

### 3.1 实时数据层

#### 3.1.1 高频数据采集
```python
# 技术选型
- 数据源策略:
  - 免费用户: Akshare (免费、3秒延迟)
  - VIP/SVIP: Tushare Pro (付费、更稳定)
  - 支持备用切换和自动降级
- 采集频率:  Level-2 行情 (3秒/次) / 逐笔成交 (事件驱动)
- 架构模式:  生产者-消费者模式 (多进程+协程)
- 关键技术:  AsyncIO + HTTP Streaming (SSE) + 连接池
```

#### 3.1.2 实时计算引擎
- **指标计算**: 实时MACD、KDJ、成交量异动、资金流向
- **技术方案**: 
  - Pandas/NumPy 向量化计算
  - Numba JIT加速关键算法
  - 滑动窗口增量计算减少重复运算
- **延迟目标**: 数据处理 < 100ms

### 3.2 多Agent决策引擎

#### 3.2.1 Agent设计
| Agent角色 | 职责 | 输入 | 输出 |
|-----------|------|------|------|
| 技术分析Agent | 分析K线形态、技术指标 | 价格/成交量/指标数据 | 技术评分 + 关键位 |
| 基本面Agent | 分析公司财务、公告 | F10数据/实时公告 | 基本面评分 |
| 情绪Agent | 分析市场情绪、板块热度 | 涨跌家数/板块排行 | 情绪评分 |
| 资金Agent | 分析资金流向、主力动向 | 大单数据/龙虎榜 | 资金评分 |
| 决策Agent | 综合决策、风险控制 | 各Agent评分 | 最终决策 + 置信度 |

#### 3.2.2 专家讨论组机制
```
流程:
1. 信号触发 → 2. 各专家Agent分析 → 3. 讨论协调器整合 → 4. 决策Agent裁决 → 5. 输出决策

讨论模式:
- 并行分析: 各Agent独立分析
- 权重投票: 根据历史成功率动态调整权重
- 异议记录: 保留不同意见用于复盘
```

### 3.4 复盘与优化引擎

#### 3.3.1 复盘流程
```
每日收盘后:
1. 归档当日所有信号和决策 → TimescaleDB
2. 批量读取历史数据 → Polars DataFrame（高性能分析）
3. 计算实际成功率 (涨停成功率/收益率) → Polars 向量化计算
4. 分析失败原因 (假突破/情绪逆转/黑天鹅) → Polars 分组聚合
5. 更新各Agent权重 → 结果写回 PostgreSQL
6. 生成复盘报告 → 可视化展示
```

**复盘技术方案**:
- **数据读取**: 从 TimescaleDB 批量读取历史K线和信号记录
- **分析引擎**: Polars（比 Pandas 快10-50倍，内存占用少6倍）
- **计算场景**: 分组聚合计算每只股票的收益表现、按Agent统计成功率、时间模式分析
- **结果存储**: 分析结果写回数据库，用于 Agent 权重调整

#### 3.4.2 Agent成长机制
- **反馈学习**: 根据复盘结果调整Agent策略参数
- **权重优化**: 动态调整各Agent在决策中的权重
- **知识库更新**: 积累成功案例和失败教训

| 消息队列/Broker | RabbitMQ | Celery Broker、任务队列、事件总线 |

> **💡 架构说明：Celery + RabbitMQ + Redis 协作方式**
> 
> 我们采用 **RabbitMQ 作为 Celery Broker**，**Redis 作为缓存和结果后端** 的组合：
> 
> ```
> ┌─────────┐      ┌─────────────┐      ┌─────────┐
> │ Celery  │ -->  │   RabbitMQ  │ -->  │ Worker  │
> │ Producer│      │   (Broker)  │      │         │
> └─────────┘      └─────────────┘      └────┬────┘
>                                             │
>                                             ▼
>                                       ┌─────────┐
>                                       │  Redis  │
>                                       │(Backend)│
>                                       └─────────┘
> ```
> 
> - **RabbitMQ (Broker)**: 负责任务队列的持久化、路由和分发，提供高可靠性和消息确认机制
> - **Redis (Backend)**: 存储任务执行结果、缓存热点数据、管理Session
> 
> **为什么不只用 Redis？**
> - RabbitMQ 提供更可靠的消息持久化和任务调度能力
> - 任务高峰期时，RabbitMQ 的队列管理能力优于 Redis
> - Redis 专注做它擅长的事：高速缓存和结果存储

### 5.2 前后端通信方案

#### 5.2.1 方案对比

| 方案 | 复杂度 | 实时性 | 适用场景 | 本项目选择 |
|------|--------|--------|----------|-----------|
| **HTTP REST** | ⭐ | ⭐⭐ | 主动查询 | ✅ 数据获取 |
| **SSE** | ⭐⭐ | ⭐⭐⭐⭐ | 单向推送 | ✅ 决策通知 |
| **WebSocket** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 双向高频 | ❌ 过度设计 |
| **Long Polling** | ⭐⭐ | ⭐⭐ | 兼容旧浏览器 | ❌ 不需要 |

#### 5.2.2 选择 SSE 的原因

**决策通知的特点**:
- 单向：服务器 → 客户端
- 低频：只在决策Agent产生结果时推送
- 文本：JSON格式决策数据
- 可靠：错过消息需要自动重连

**SSE 优势**:
```
✓ 基于标准 HTTP，无需额外协议
✓ 浏览器原生支持 EventSource API
✓ 自动重连（浏览器内置）
✓ 无连接数限制（相对 WebSocket）
✓ 可穿透企业防火墙/Nginx
✓ 断线后自动恢复，无需手动处理
```

**WebSocket 在本项目中的问题**:
```
✗ 需要维护长连接状态
✗ 需要心跳保活机制
✗ 需要手动处理重连
✗ 额外的库依赖 (socket.io)
✗ 对决策通知场景过度设计
```

#### 5.2.3 通信策略

```
前端请求                    后端响应
─────────                  ─────────
GET  /api/stocks           → 股票列表 (REST)

## 6. 实时性保障策略

### 6.1 数据层面
- **本地缓存**: Redis缓存热点数据，减少数据库查询
- **增量更新**: 只传输变化的数据，减少网络开销
- **数据预计算**: 盘前预加载历史指标，盘中增量更新

### 6.2 计算层面
- **异步架构**: 全程AsyncIO，避免阻塞
- **并行计算**: 多进程处理不同股票，多线程处理不同指标
- **算法优化**: Numba加速关键计算路径

### 6.3 推送层面
- **HTTP SSE**: 轻量级单向推送，浏览器原生支持自动重连
- **消息合并**: 高频变动合并推送，避免消息风暴
- **分级推送**: 重要信号优先推送，普通数据批量推送

## 9. 数据同步层 (Data Sync Layer)

### 9.1 设计目标

为了解决外部数据源不稳定、API限制等问题，引入本地数据缓存层：

1. **数据稳定性**: 近14天数据存储在本地RDS，减少对外部API的依赖
2. **加工灵活性**: 本地数据便于批量查询、聚合计算、历史回测
3. **成本优化**: 减少付费API调用次数
4. **访问速度**: 本地查询延迟 < 10ms，外部API可能 > 500ms

### 9.2 同步策略

```
┌─────────────────────────────────────────────────────────────────┐
│                      数据同步策略                                │
├─────────────────────────────────────────────────────────────────┤

│  │  首次启动    │    │  每日收盘后  │    │  实时触发    │      │
│  │  (全量同步)  │    │  (增量同步)  │    │  (按需补全)  │      │
│  └──────┬───────┘    └──────┬───────┘    └──────┬───────┘      │

### 9.3 API数据获取策略

```python
# 数据获取优先级
1. 本地缓存 (14天内日线数据)
   └── 数据完整性 >= 50% ? 直接返回 : 异步触发同步
   
2. 外部数据源
   └── 本地无数据 或 查询超过14天 或 force_refresh=true
       └── 根据用户等级选择: Akshare (免费) / Tushare Pro (VIP)
```

### 9.4 定时任务调度

| 任务 | 调度时间 | 说明 |
|------|----------|------|
| daily-incremental-sync | 15:35 | 收盘后增量同步当日数据 |
| data-completeness-check | 每小时 | 检查数据完整性，自动补全 |
| cleanup-old-data | 02:00 | 清理14天前的过期数据 |
